# Архітектура класів та шаблони проектування (Class Diagram)

Дана діаграма класів відображає технічну архітектуру системи **StaffFlow HRM**. Для забезпечення масштабованості та відповідності вимогам веб-розробки, система спроектована з використанням модульної архітектури, принципів **SOLID**, базових патернів **GRASP** та 5 шаблонів проектування **GoF**.

## Архітектурні рішення (GRASP та REST)
* **REST-підхід:** Взаємодія з клієнтом відбувається через контролери (`EmployeeController`, `LeaveController`), які приймають JSON-запити.
* **GRASP Controller:** Контролери не містять бізнес-логіки. Вони лише делегують запити відповідним сервісам чи фасадам, виконуючи роль "Регулювальника".
* **Layered Architecture:** Система логічно розділена на шар маршрутизації (API & Controllers), шар бізнес-логіки (доменні пакети) та шар доступу до даних (Data Access).

## З астосовані патерни GoF

1. **Facade (Фасад) — *Колір: Червоний***
   * **Клас:** `OnboardingFacade`
   * **Призначення:** Процес оформлення нового співробітника вимагає створення запису в БД, ініціалізації об'єкта та генерації контракту. Фасад приховує цю структурну складність від контролера, надаючи єдиний метод `onboardNewEmployee()`.

2. **Composite (Компонувальник) — *Колір: Синій***
   * **Класи:** `IOrganizationUnit`, `Employee`, `Department`
   * **Призначення:** Дозволяє працювати з ієрархією компанії. Метод `getBudget()` можна викликати як для окремого працівника (поверне його ЗП), так і для цілого відділу (поверне суму ЗП всіх працівників та підвідділів).

3. **State (Стан) — *Колір: Зелений***
   * **Класи:** `LeaveRequest`, `ILeaveState`, `PendingState`, `ApprovedState`
   * **Призначення:** Керує життєвим циклом заявки на відпустку. Заявка змінює свою поведінку (наприклад, можливість скасування) залежно від її поточного стану. 

4. **Strategy (Стратегія) — *Колір: Жовтий***
   * **Класи:** `PayrollService`, `IPayrollStrategy`, `FullTimeStrategy`, `HourlyStrategy`
   * **Призначення:** Відокремлює алгоритми розрахунку зарплати від самого сервісу. Це дозволяє динамічно підміняти формули розрахунку для штатних працівників та контракторів.

5. **Factory Method (Фабричний метод) — *Колір: Фіолетовий***
   * **Класи:** `DocumentFactory`, `HRDocumentFactory`, `IDocument`
   * **Призначення:** Делегує процес створення кадрової документації спеціалізованим підкласам. Система може створювати контракти, накази чи довідки за єдиним інтерфейсом.

## Виконання принципів SOLID

В архітектурі системи StaffFlow суворо дотримано всіх п'яти принципів об'єктно-орієнтованого дизайну:

* **S — Single Responsibility Principle (Принцип єдиної відповідальності):**
  Кожен клас має лише одну причину для змін. Наприклад, `LeaveController` відповідає виключно за маршрутизацію REST-запитів, `LeaveRequest` зберігає контекст заявки, а конкретні стани (`PendingState`) керують логікою переходів. Контролер не займається бізнес-логікою, а класи бізнес-логіки не знають про HTTP-запити.

* **O — Open/Closed Principle (Принцип відкритості/закритості):**
  Завдяки патерну *Strategy*, для додавання нового типу оплати (наприклад, `FreelanceStrategy` або `GigContractStrategy`) нам достатньо створити новий клас. Нам не потрібно вносити зміни (модифікувати) існуючий код у `PayrollService`. Система відкрита для розширення, але закрита для модифікації.

* **L — Liskov Substitution Principle (Принцип підстановки Барбари Лісков):**
  Будь-який клас, що реалізує інтерфейс `IDocument` (наприклад, `ContractDocument`), може бути використаний об'єктом `DocumentFactory` без порушення роботи системи. Те саме стосується станів відпустки: `LeaveRequest` може без проблем працювати з будь-яким об'єктом, що наслідує `ILeaveState`, не знаючи його конкретного типу.

* **I — Interface Segregation Principle (Принцип розділення інтерфейсу):**
  Замість створення одного глобального інтерфейсу (наприклад, `IHRMSystem`), який змушував би класи реалізовувати непотрібні їм методи, ми створили вузькоспеціалізовані інтерфейси: `IPayrollStrategy`, `ILeaveState`, `IOrganizationUnit`, `IDocument`. Класи залежать лише від тих методів, які вони реально використовують.

* **D — Dependency Inversion Principle (Принцип інверсії залежностей):**
  Модулі верхнього рівня (бізнес-логіка, наприклад `OnboardingFacade`) не залежать від модулів нижнього рівня (конкретної бази даних `PostgresEmployeeRepo`). Обидва шари залежать від абстракції — інтерфейсу `IEmployeeRepository`. Це дозволяє легко змінити тип бази даних без переписування ядра системи.
