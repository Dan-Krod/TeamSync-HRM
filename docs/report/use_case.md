# Архітектура прецедентів (Use Cases) системи StaffFlow

Цей документ описує базову архітектуру, ролі користувачів та ключові бізнес-процеси інформаційної системи управління персоналом **StaffFlow**, відповідно до Use Case діаграми.

## Актори системи

У системі реалізовано чітке розмежування прав доступу шляхом ізоляції акторів та їхніх функціональних модулів:

### Первинні актори (Ініціатори)
1. **Співробітник (Employee):** Базовий авторизований користувач. Має доступ до порталу самообслуговування (ESS), де може керувати своїм робочим часом та відсутністю.
2. **Керівник відділу (Department Manager):** Управлінець, який приймає рішення щодо запитів своєї команди (відпустки, овертайми) та проводить оцінку продуктивності.
3. **HR-менеджер (HR Manager):** Адміністратор системи, відповідальний за кадровий обіг (найм, звільнення) та фінансові розрахунки (зарплата, податки).
4. **Кандидат (Candidate):** Неавторизований зовнішній користувач, який взаємодіє виключно з модулем рекрутингу для подачі заявок на відкриті вакансії.

### Системні та зовнішні актори
1. **Системний планувальник (<<Timer>>):** Автоматизований фоновий процес (cron-job), який за розкладом ініціює рутинні задачі, такі як щомісячний розрахунок заробітної плати.
2. **Поштовий шлюз (<<External System>>):** Сторонній сервіс (наприклад, SMTP/SendGrid), що приймає дані від системи для розсилки email-сповіщень.
3. **Банківське API (<<External API>>):** Зовнішній фінансовий шлюз, який приймає згенеровані зарплатні відомості для проведення виплат.

## Основні модулі та залежності

Система побудована з використанням відношень `<<include>>` (обов'язкове включення) та `<<extend>>` (розширення за певної умови).

### 1. Аутентифікація
Абстрактний процес "Авторизація в системі" реалізується через два можливих розширення (`<<extend>>`): **Вхід через SSO** (наприклад, корпоративний Google акаунт) або традиційний **Локальний вхід**.

### 2. Employee Self-Service (ESS)
* **Робочий час:** Співробітник керує своїм графіком. За потреби цей процес розширюється (`<<extend>>`) подачею **Запиту на овертайм**.
* **Відсутність:** Базове управління відсутністю обов'язково включає (`<<include>>`) **Перевірку балансу днів**. Якщо співробітник оформлює лікарняний (`<<extend>>`), система вимагає **Завантаження медичної довідки** (`<<include>>`).

### 3. Managerial Operations
* Керівник обробляє запити команди, що може призвести до **Ухвалення** або **Відхилення** запиту (`<<extend>>`). 
* Процес **Оцінки продуктивності** обов'язково включає (`<<include>>`) **Встановлення KPI** на наступний період.

### 4. HR-адміністрування
* **Кадровий рух:** Оформлення найму обов'язково запускає **Процес онбордингу** (`<<include>>`). Аналогічно, оформлення звільнення вимагає негайного **Анулювання доступу** (`<<include>>`).
* **Зарплата:** Ініційований HR-ом або Планувальником розрахунок ЗП обов'язково включає **Розрахунок податків** та **Генерацію банківської відомості** (`<<include>>`), яка потім передається до Банківського API.

### 5. Рекрутинг
* Подача заявки кандидатом вимагає **Завантаження резюме** (`<<include>>`). За успішного розгляду процес розширюється **Проведенням співбесіди** (`<<extend>>`).

### 6. Системні сповіщення
Будь-які критичні зміни статусу (ухвалення/відхилення відпустки, анулювання доступу, оформлення найму) автоматично генерують сповіщення (`<<include>>`), яке відправляється на зовнішній Поштовий шлюз.
